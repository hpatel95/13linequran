## 2. Project Context & Current State

### 2.1 The Objective
The goal is to deliver an authentic, offline-first iOS application (iOS 17.0+, Swift 5.9 / Swift 6 concurrency safe) tailored specifically for Hifz (memorization) students and readers who require the classic **13-line Indo-Pak Mushaf layout**. Key functional requirements include:
1. Exact visual reproduction of the physical lithograph (illuminated arches on Pages 1 & 2, shaded Juz banners, margin rukus, Tajweed colors, and concluding *Dua Khatam al-Quran*).
2. Per-Ayah interactive gestures (long-press to select, inspect translations, copy, bookmark, or play audio).
3. Synchronized audio recitation (verse-by-verse playback highlighting each Ayah as recited by Sheikh Khalifa Al Tunaiji, with smooth cross-page continuation handling).
4. Multi-language translations (Saheeh International, Hilali & Khan, Hamidullah French).
5. Offline full-text search (FTS5) across Arabic and translation texts.
6. RTL (right-to-left) pagination matching a physical book.

### 2.2 What Was Built (Phases 1–6)
- A local canonical SQLite database (`quran_content.sqlite`) containing 114 Surahs, 6,236 Ayahs, 11,037 lines of text, 3 translations, and an FTS5 search index (passing 51/51 automated integrity checks).
- An Audio Player service (`AudioPlayerService`) streaming recitations from Sheikh Khalifa Al Tunaiji with verse sync and local-first cached file lookup.
- A synthetic text rendering pipeline using Core Text (`MushafPageGrid`, `MushafTextSource`, `MushafTextLayoutEngine`, `MushafTextCanvas`).
- Full unit test and UI test suites passing green on GitHub Actions CI (`build-ipa.yml`).

## 3. Detailed Diagnosis: Current Defects & Audit Reconciliations

Visual inspection of screenshots generated by our CI pipeline (`Quran13Line-verification/screenshots/compact/`) against expected reference pages (`Quran13Line-verification/expected/`) identified six critical discrepancies:

```

| Feature                            | Current Synthetic Font Engine    | Authentic Reference Mushaf |
+------------------------------------+----------------------------------+----------------------------+
| Page 1 (Al-Fatihah)                | 8 lines text + 5 empty lines     | Illuminated Arch + Border  |
| Page 2 (Al-Baqarah 1-5)            | 8 lines text + 5 empty lines     | Illuminated Arch + Border  |
```

### Critical Audit Findings Reconciled
1. **The 849 vs 847 Page Difference**:
   - The canonical text database uses an **849-page Qudratullah layout**.
   - The reference scanned dataset from Qamar Apps contains **847 Quran-bearing pages (Taj Company edition)**, plus cover/front matter and the 2-page *Dua Khatam al-Quran*.
   - The verse offsets vary between 0 and 4 pages; only 242 of 849 pages share the identical set of verses.
   - **Resolution**: We DO NOT rename Qamar files to fit the 849-page schema. Instead, we formally adopt the **Taj Company 847-Quran-page standard** for the authentic facsimile reader, hosted in a separate sidecar database (`mushaf_editions.sqlite`), while keeping the existing 849-page Core Text renderer as `legacy-qudratullah-13-849` for accessible text fallback. Canonical content (`quran_content.sqlite`) remains completely untouched.
2. **Defective Coordinates in Source 522**:
   - Source `522.html` in the Qamar dataset contains `coords="0,0,0,0"` for verses 26:143 and 26:144.
   - **Resolution**: An explicit, versioned correction patch will be applied during ingestion so all 6,236 verses have valid interactive bounding boxes.
3. **Aspect-Fit Touch Geometry**:
   - Naively scaling $X$ and $Y$ by container dimensions introduces massive touch errors on letterboxed screens.
   - **Resolution**: Use normalized coordinates $[0, 1]$ and strictly compute letterboxing offsets $ox$ and $oy$.
4. **Rejection of Generative AI Upscaling**:
   - Generative super-resolution risks hallucinating or altering sacred Arabic diacritics, dots, vowels, and Tajweed color boundaries.
   - **Resolution**: We reject generative AI upscaling and use genuine, high-fidelity publisher scans.

## 4. Empirical Verification of Native Higher-Resolution Scans

In the Source Research Addendum, Qamar's first-party web eBook (`https://ebooks.qamarapps.com/ebooks/quran-13-line/HTML/`) was identified as serving **1162 × 1684 px** PNG images.

We empirically downloaded and compared `page0006.png`, `page0007.png`, and `page0008.png` against APK pages `004.png`, `005.png`, and `006.png`:
- **Identity Confirmed**: Visual inspection confirms **100% calligraphic and lithographic identity**. The calligraphy, word breaks, Harakat, Tajweed colors, illuminated arches, and margin rukus are identical.
- **Why Automated Correlation Failed**: The web eBook includes a 40px **Tajweed rule legend bar** along the bottom edge (`Ikhfa | Qalqala | Ghunna | Idghaam...`). The aspect ratio is $1162/1684 \approx 0.690$ compared to the APK's $720/1057 \approx 0.681$.
- **Pagination Mapping**: The correspondence is an exact constant index offset:
  $$\text{Web\_Page\_Number} = \text{APK\_Page\_Number} + 2$$
  - APK `004.png` (book page 4, Al-Fatihah) $\iff$ Web eBook `page0006.png`
  - APK `005.png` (book page 5, Al-Baqarah 1–5) $\iff$ Web eBook `page0007.png`
  - APK `006.png` (book page 6, Al-Baqarah 6–13) $\iff$ Web eBook `page0008.png`
  - APK `850.png` (book page 850, An-Nas) $\iff$ Web eBook `page0852.png`

### 5.1 Sidecar Database Schema (`mushaf_editions.sqlite`)

```sql
PRAGMA foreign_keys = ON;
PRAGMA user_version = 1;

CREATE TABLE metadata (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL
);

CREATE TABLE canonical_verses (
    surah_id INTEGER NOT NULL CHECK(surah_id BETWEEN 1 AND 114),
    ayah_number INTEGER NOT NULL CHECK(ayah_number > 0),
    canonical_id INTEGER NOT NULL UNIQUE,
    PRIMARY KEY (surah_id, ayah_number)
);

CREATE TABLE editions (
    edition_id TEXT PRIMARY KEY,
    content_version INTEGER NOT NULL CHECK(content_version > 0),
    display_name TEXT NOT NULL,
    publisher TEXT NOT NULL,
    renderer_kind TEXT NOT NULL CHECK(renderer_kind IN ('legacyText','facsimile')),
    approval_status TEXT NOT NULL CHECK(approval_status IN ('fixture','unapproved','approved')),
    quran_page_count INTEGER NOT NULL CHECK(quran_page_count > 0),
    navigation_page_count INTEGER NOT NULL CHECK(navigation_page_count >= quran_page_count),
    notice_path TEXT
);

CREATE TABLE pages (
    edition_id TEXT NOT NULL,
    page_id TEXT NOT NULL,
    navigation_index INTEGER NOT NULL CHECK(navigation_index > 0),
    quran_ordinal INTEGER CHECK(quran_ordinal > 0),
    printed_label TEXT,
    kind TEXT NOT NULL CHECK(kind IN ('quran','quranAndSupplement','supplement','frontMatter')),
    title TEXT NOT NULL,
    source_asset_id TEXT NOT NULL,
    source_width INTEGER,
    source_height INTEGER,
    image_path TEXT,
    image_sha256 TEXT,
    PRIMARY KEY (edition_id, page_id),
    UNIQUE (edition_id, navigation_index),
    UNIQUE (edition_id, quran_ordinal),
    UNIQUE (edition_id, source_asset_id),
    FOREIGN KEY (edition_id) REFERENCES editions(edition_id),
    CHECK (
      (kind IN ('quran','quranAndSupplement') AND quran_ordinal IS NOT NULL)
      OR (kind IN ('supplement','frontMatter') AND quran_ordinal IS NULL)
    )
);

CREATE TABLE page_verses (
    edition_id TEXT NOT NULL,
    page_id TEXT NOT NULL,
    surah_id INTEGER NOT NULL,
    ayah_number INTEGER NOT NULL,
    reading_order INTEGER NOT NULL CHECK(reading_order > 0),
    starts_here INTEGER NOT NULL CHECK(starts_here IN (0,1)),
    ends_here INTEGER NOT NULL CHECK(ends_here IN (0,1)),
    PRIMARY KEY (edition_id, page_id, surah_id, ayah_number),
    UNIQUE (edition_id, page_id, reading_order),
    FOREIGN KEY (edition_id, page_id) REFERENCES pages(edition_id, page_id),
    FOREIGN KEY (surah_id, ayah_number) REFERENCES canonical_verses(surah_id, ayah_number)
);
CREATE INDEX idx_page_verses_key ON page_verses(edition_id, surah_id, ayah_number);

CREATE TABLE regions (
    edition_id TEXT NOT NULL,
    page_id TEXT NOT NULL,
    region_id TEXT NOT NULL,
    kind TEXT NOT NULL CHECK(kind IN ('ayah','bismillah','decoration','supplication')),
    surah_id INTEGER,
    ayah_number INTEGER,
    fragment_order INTEGER NOT NULL CHECK(fragment_order > 0),
    source_order INTEGER NOT NULL CHECK(source_order > 0),
    label TEXT,
    min_x REAL NOT NULL CHECK(min_x >= 0 AND min_x < 1),
    min_y REAL NOT NULL CHECK(min_y >= 0 AND min_y < 1),
    max_x REAL NOT NULL CHECK(max_x > 0 AND max_x <= 1 AND max_x > min_x),
    max_y REAL NOT NULL CHECK(max_y > 0 AND max_y <= 1 AND max_y > min_y),
    PRIMARY KEY (edition_id, page_id, region_id),
    UNIQUE (edition_id, page_id, source_order),
    UNIQUE (edition_id, page_id, surah_id, ayah_number, fragment_order),
    FOREIGN KEY (edition_id, page_id) REFERENCES pages(edition_id, page_id),
    FOREIGN KEY (edition_id, page_id, surah_id, ayah_number)
      REFERENCES page_verses(edition_id, page_id, surah_id, ayah_number)
);
CREATE INDEX idx_regions_verse ON regions(edition_id, surah_id, ayah_number);

CREATE TABLE navigation_anchors (
    edition_id TEXT NOT NULL,
    kind TEXT NOT NULL CHECK(kind IN ('surah','juz')),
    number INTEGER NOT NULL,
    page_id TEXT NOT NULL,
    surah_id INTEGER NOT NULL,
    ayah_number INTEGER NOT NULL,
    PRIMARY KEY (edition_id, kind, number),
    FOREIGN KEY (edition_id, page_id, surah_id, ayah_number)
      REFERENCES page_verses(edition_id, page_id, surah_id, ayah_number)
);
```

### 5.2 Mathematical Aspect-Fit Coordinate Transform

For an image of size $(W, H)$ displayed inside a container of size $(V_w, V_h)$:

$$s = \min\left(\frac{V_w}{W}, \frac{V_h}{H}\right)$$
$$\text{imageWidth} = W \cdot s, \quad \text{imageHeight} = H \cdot s$$
$$ox = \frac{V_w - \text{imageWidth}}{2}, \quad oy = \frac{V_h - \text{imageHeight}}{2}$$

**Container Touch Point $(touchX, touchY) \to$ Normalized Coordinates $(u, v)$**:
$$u = \frac{touchX - ox}{\text{imageWidth}}, \quad v = \frac{touchY - oy}{\text{imageHeight}}$$
*Touches with $u < 0$, $u \ge 1$, $v < 0$, or $v \ge 1$ are strictly rejected as outside the page.*

**Normalized Region $[\text{minX}, \text{minY}, \text{maxX}, \text{maxY}] \to$ Container Highlight Rect**:
$$x = ox + \text{minX} \cdot \text{imageWidth}, \quad y = oy + \text{minY} \cdot \text{imageHeight}$$
$$\text{width} = (\text{maxX} - \text{minX}) \cdot \text{imageWidth}, \quad \text{height} = (\text{maxY} - \text{minY}) \cdot \text{imageHeight}$$

*Because coordinates are stored in normalized $[0, 1]$ space, switching between 720p and 1162p requires zero coordinate mutation.*
